# Hikmah 受控任务交付规范

适用于目标明确、上下文有限的执行型研发人员与 luna worker。目标是让正确推进依赖于清楚的输入、约束和验证，而不依赖执行者临场补完架构。此文不启动子代理；团队并行仍须用户明确授权。

## 1. 职责与决策边界

| 角色 | 对结果负责 | 不得转交给 worker 的判断 |
|---|---|---|
| 产品负责人 | 目标、优先级、数据授权、业务验收、能力开放 | 用试点替代完整承诺、改变隐私/规模边界、接受重大风险 |
| 技术负责人 | 上游契约实证、技术选型、威胁模型、任务拆分、接口冻结、回退设计 | 猜测 Hook/发送拦截能力、选择认证机制、解决跨系统一致性、安全门禁放行 |
| 实施 worker | 单卡允许路径内的代码、测试、文档和证据 | 改版本/接口/授权规则、扩大读写范围、自己豁免测试或发布 |
| 评审责任人 | 对照规范检查行为、复现关键断言、验收证据层级 | 把“worker 已完成”或测试数量当作通过 |

角色可以由同一个人按阶段承担，但实施和验收应分开复核；安全/身份/持久化/外部副作用由具备相应判断能力的负责人验收。无需为每张卡启动新 Agent，也不以某个模型名称作为质量保证。

## 2. 四层文档与状态

| 层 | 回答的问题 | 维护者 |
|---|---|---|
| 路线图 | 做到什么终态，哪些方向不能走，按什么证据开放 | 产品/技术负责人 |
| 工作包 | 一个能力切片如何集成、有哪些风险门禁 | 技术负责人 |
| 任务卡 | 现在只改哪些文件，先跑什么失败测试，如何交付 | 技术负责人冻结，worker 执行 |
| 证据记录 | 在什么基线和环境下实际证明了什么 | worker 记录，评审责任人核验 |

原 P0/P1/P2 的 14 项是工作包，不能把一整个“OAuth 身份”“知识撤回”直接当作单 worker 任务。分解顺序见[工作项队列](plans/2026-09-05-work-item-sequence.md)。

任务同时记录两类独立状态：

- 准备度：`outlined`（拆分已定义）→ `specified`（完整卡与接口已写）→ `ready`（负责人核验契约/前置证据可分派）。接口或上游证据失效时退回 `specified`。
- 执行状态：`not_authorized` → `authorized` → `in_progress` → `in_review` → `verified`；发生缺依赖/边界冲突为 `blocked`，必须记录原因和恢复条件。

只有 `ready + authorized + 前置卡 verified` 才能领取。文档 `review`、完成静态检查或用户批准总体方向均不能自动变成 `verified`。相反，已经明确覆盖本卡动作的实施授权不要求重复确认。

## 3. 任务卡的入场条件

每张卡必须包含以下内容，缺一项由技术负责人补齐后再分派：

1. 唯一 ID、阶段/工作包、一个可观察结果、失败会影响谁。
2. 精确基线 commit、前置卡及其证据；本卡可用的工具链与隔离环境。
3. 只读输入和允许修改的精确路径；禁止目录和外部动作；文件新增/修改明确区分。
4. 消费/产生的完整类型、函数签名、HTTP 字段/状态码、事务与幂等边界。枚举值来自事实源，示例不可虚构上游 API。
5. 固定合成输入、正向和负向预期、完整 imports/fixture 生命周期，以及实际检查可观察结果的测试。
6. 小步骤：写失败用例→执行并说明失败原因→实现→执行通过→检查差异→提交证据。单步骤只有一个动作，不用“一次实现全部认证/恢复”概括系统设计。
7. 精确验证命令、执行目录、预计产生的断言/制品；说明 mock、契约和 E2E 分别证明什么。
8. 停止条件、保护用户现有数据/改动的回退方式、需要负责人决定的事项。
9. 提交范围和评审人；公共接口同步 Client/Web/文档，CI 纳入新增测试。

卡片应让 worker 无需新选组件、发明数据协议或查询不确定上游入口即可实现。如果一张卡包含两个可独立拒绝的结果，拆成两张；通常只覆盖一个生产职责和对应测试，跨边界必要修改逐个列出理由。禁止用固定行数/时间掩盖合理的原子变更。

## 4. 技术方案的科学性检查

负责人冻结卡片前，逐项完成：

| 检查 | 可接受的证据 | 不足以分派的写法 |
|---|---|---|
| 可实现 | 固定公开接口的签名、最小真实调用/故障实验、未支持入口关闭方案 | “应该有 Hook”“按官方接口实现” |
| 最小性 | 直接复用的能力及必须自建的窄差异，失败回退可描述 | 为未知将来引入通用框架 |
| 正确性 | 受信输入、状态转移、事务/并发/重放、取消/未知结果均有用例 | 只给 happy path 或同文件测试自己的常量函数 |
| 隔离 | 授权主体、对象与目标受众；前置读取和最终发送各自检查 | 只验证 UI/请求者，忽略 Bot/会话/缓存 |
| 可运维 | 配置来源、密钥引用、超时、观测、迁移/恢复边界 | 命令退出 0 就称可恢复 |
| 可测量 | 预先冻结数据、分母、对照、样本和失败处理 | 先看到结果再改目标或挑成功样本 |

技术问题不确定时先交付负责人拥有的资格实验卡；其输出是通过/失败/未运行和原始证据，不要求 worker 自行“想办法通过”。实验失败同样是有效交付，但不能解锁依赖该能力的实现。

## 5. worker 的固定执行流程

1. 核验基线和工作区状态；有未知修改保持原样，确认允许路径。读取本卡引用的精确输入，不能默认继承其他任务聊天。
2. 核验 `ready`、授权和前置证据。只领取一张卡；维护同一数据库迁移、共享契约或配置的任务串行。
3. 写负向测试并运行。必须确认因目标行为缺失而失败；若失败来自误连、工具缺失或配置不符，先记录环境阻塞。
4. 在允许路径实现最小行为。测试文件导入生产代码；测试替身只能替代明确的外部边界，不能替代待验证的授权或事务逻辑。
5. 跑本卡针对性验证和适用质量门禁；预期不符先定位一个根因，不扩大范围重构。不删除失败断言、增加无解释 skip、降低严格类型或用 mock 成功换取绿灯。
6. 自审 diff，确认没有改动不允许路径、凭据/真实正文、锁版本或策略。提交只包含本卡改动。
7. 提交交接记录，进入 `in_review`；评审人复核后才变 `verified`，集成工作包和能力开放另行验收。

## 6. 停止、升级和恢复

立即停止本卡的条件：目标上游无公开能力；配置/凭据/数据库不是获准目标；需要修改接口/版本/安全边界；实际调用越权；用户未知改动冲突；验证会覆盖或删除非测试数据；测试结果与规范冲突。

同一失败完成两轮有具体假设的局部修复仍未消除，或连续两次需要超出允许路径时，提交阻塞记录给技术负责人。记录：任务 ID、基线、最小输入、期望/实际、尝试与证据、影响范围、所需决定。不得无限重试或把猜测作为补丁提交。

回退先停止新工作，保留 diff 和证据；本卡新增且无用户数据的制品可以由负责人决定撤销。涉及数据库/已发消息/部署版本时仅使用获准回退方案；不得 `reset --hard`、清业务库或删除数据卷。上下文恢复后按卡片、commit 和证据继续，不凭摘要重新执行未知状态操作。

## 7. 固定交接记录

每次交付在对应 Issue/PR 记录下表，值必须来自本次执行。尚未取得的项目写 `not_run` 或 `blocked` 并说明原因；不能编造 commit、测试数量、环境或复核人。

| 字段 | 必须提供的内容 |
|---|---|
| identity | 卡片 ID、基线 commit、交付 commit、关联工作包/Issue |
| scope | 实际修改路径及各自作用，超出白名单则不能送审 |
| contract | 消费/产生接口版本，是否与冻结卡一致 |
| red | 失败用例、命令、失败断言和原因 |
| green | 命令、断言摘要、执行时间、脱敏完整输出引用 |
| limitations | 未运行环境、mock 边界、未解决问题和剩余风险 |
| rollback | 本卡回退步骤及是否涉及持久数据 |
| review | 评审人、结论、日期；未复核时保持 in_review |

每工作包完成后由技术负责人先做规范审查，再做实现/集成审查。仅一张卡通过不能声称工作包、阶段或产品完成。详细规格按实际已验证前置 commit 滚动更新，避免提前写死尚不存在的集成细节。
